ОЖИДАЕМЫЙ РЕЗУЛЬТАТ
- Каждый из 22 production-route воспроизводит правильное состояние, данные и интерактивные слои исходного кадра.
- Геометрия, типографика, цвета, прозрачность, SVG/PNG, медицинские изображения, графики, таблицы, формы, overlay, z-index и состояния совпадают с соответствующим PNG.
- Для каждого route сохранены reference, actual, absolute diff, overlay 50/50 и метрики AE/RMSE.
- После последней правки выполнен полный повторный прогон всех 22 экранов в одинаковом окружении.
- Строгая цель — AE=0 на всех 22 кадрах. Если хотя бы один кадр не достиг AE=0, не называй результат 100% pixel-perfect: укажи PARTIAL, точные остаточные зоны, метрики и причинные гипотезы.

ГРАНИЦЫ
- Прочитай действующие инструкции проекта, README, package.json, маршруты, компоненты, CSS, ассеты, шрифты и текущий audit script до изменений.
- Сохраняй существующий стек и компоненты. Не добавляй библиотеку, если задача решается штатными средствами.
- Не заменяй точный ассет эмодзи, Unicode-глифом, случайной иконкой, CSS-имитацией или похожей картинкой.
- Не обновляй, не маскируй и не перерисовывай golden PNG, чтобы скрыть расхождение. Не ослабляй diff-порог.
- Не фиксируй симптом локальными magic numbers, пока не определена общая причинная группа и затронутые экраны.
- Не меняй production до локальной сборки, тестов и полного screenshot/diff. После публикации отдельно повтори те же 22 проверки на production.

FIGMA MCP — ИСТОЧНИК ДИЗАЙНА
1. Используй get_metadata только как карту большого файла. Для каждого экрана работай с точным node ID из таблицы.
2. Для точного node вызови get_design_context, затем get_variable_defs и get_screenshot. Если есть инстансы, вызови get_code_connect_map и переиспользуй реальные компоненты.
3. Для растров, SVG и исходных изображений используй download_assets; сохраняй исходный формат и размеры. Не считай screenshot заменой структурного context.
4. Если один frame слишком тяжёлый, разбивай его на логические секции/компоненты и запрашивай их отдельно.
5. Отделяй подтверждённые Figma-значения от вычисленных по PNG и от допущений.

ИНВЕНТАРЬ ПЕРЕД ПРАВКАМИ
Составь таблицу по каждому из 22 кадров: node ID, route, крупные области, повторные компоненты, уникальные элементы, состояние, шрифты, ассеты, цвета, spacing/radius, overlay и самые крупные diff-регионы. Сопоставь каждый Figma-компонент с существующим компонентом кода. Найди системные причины, влияющие сразу на несколько кадров.

ЦИКЛ ИСПРАВЛЕНИЯ
1. Сортируй причины по охвату и площади diff: окружение/шрифт → общий shell/header → layout/grid → панели → типографика → ассеты → цвета/эффекты → уникальные состояния.
2. Меняй одну причинную группу за раз. До правки запиши гипотезу и список затронутых кадров.
3. После правки запускай targeted screenshots/diff всех затронутых кадров. При ухудшении откати только свою candidate-правку.
4. Правку принимай только при измеримом улучшении и отсутствии новой регрессии в соседних состояниях.
5. Для точной локализации используй overlay, difference heatmap, bounding box, DOM/computed styles и значения Figma. Не подбирай CSS вслепую.
6. После стабилизации каждой группы запускай полный прогон 22/22. После любой новой правки счёт финальных последовательных прогонов начинается заново.

Фактический инвентарь интерфейса

Сводка по 22 исходным PNG и текущей реализации. Числа, полученные из кода, всё равно должны быть перепроверены через Figma variables/computed styles.

Типографика

Manrope, кириллица; веса 400/500/600/700. Основной текст 12–18 px, заголовки 20/26/28 px. Проверять реальный загруженный файл, line box, baseline, wrap и font smoothing.

Сетка и интервалы

1920×1080; header 80 px; повторяются шаги 4/8/12/16/20/24/32/40 px. Картотека — 4 колонки; patient — профиль + main; workspace — canvas + side panel.

Формы поверхности

Карточки, поля, панели и modal используют радиусы 8/12/16/20/32 px и pill. Есть 1 px borders, мягкие тени, overflow/clipping и скруглённый верх main surface.

Палитра

Светлые white/blue-gray surfaces, почти чёрный ink, серые secondary, фирменный синий. Статусы: green/red/purple/yellow. Dark: #16151a и #2b2a2f как наблюдаемые токены реализации.

Почему промпт устроен так

Короткая схема, собранная из официальных рекомендаций OpenAI, Figma MCP и Playwright.

Outcome first

Сначала результат, критерии успеха, ограничения, evidence и stopping rule; микро-шаги задаются только там, где порядок критичен.

Точный контекст

Большой Figma-файл сначала картируется metadata, затем каждый node читается через design context, variables и screenshot.

Системные причины

Повторные компоненты, variables, Auto Layout и Code Connect уменьшают локальные расхождения и дублирование.

Одинаковая среда

Browser screenshots чувствительны к ОС, версии, headless mode и шрифтам. Baseline и actual сравниваются в закреплённом окружении.

Проверка результата

Каждая candidate-правка принимается по measured delta; после последней правки заново проверяются все 22 production routes.

Источники практик

Использованы официальные страницы, а не подборки готовых «магических» промптов.
